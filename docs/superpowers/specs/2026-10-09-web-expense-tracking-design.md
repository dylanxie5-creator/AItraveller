# 智游足迹网页版：行程花销设计规格

日期：2026-10-09

## 1. 目标与范围

在现有本地网页版的正式行程之上增加个人花销记录。手工创建和由 AI 攻略转换得到的行程使用同一套功能。用户可以在一趟行程内新增、查看、编辑和删除花销，管理仅对当前行程有效的自定义分类，并查看预算、分类和城市统计。

本阶段继续保持本地单用户产品边界：数据写入当前 SQLite 数据库，仅监听 `127.0.0.1`，不新增登录、云同步、分享或互联网部署。花销数据不发送给 AI 模型、检索服务或其他第三方。

本阶段不包含同行人 AA、付款人、分摊、小票图片、外币换算、退款或负数冲销、趋势图表，以及跨行程复用自定义分类。

## 2. 已确认的产品规则

- 每笔记录整笔人民币总金额，不按同行人数拆分。
- 金额必须大于 0，最多两位小数；保存时精确转换为整数分。
- 字段包括金额、分类、城市、日期和可选备注。
- 城市归属可选；未选择时归入“整个行程”。
- 日期必填且必须位于行程起止日期内。新增时优先使用今天；今天不在范围内时使用行程开始日。
- 备注最多 200 个字符。
- 默认分类为交通、住宿、餐饮、门票、购物、娱乐和其他。
- 自定义分类只在当前行程有效，支持新增、重命名和删除。
- 同一行程内，自定义分类不得与默认分类或其他自定义分类重名。
- 正在被花销使用的自定义分类不能删除，必须先修改相关花销。
- 超过预算仍可继续记录；预算剩余显示负数和“已超预算”文字。
- 路线后来移除城市时，历史花销保留原城市代码和名称，并标记“已移出路线”。

## 3. 选定方案

采用现有 SQLite 数据库内的关系表方案，不把花销 JSON 塞进行程负载，也不建立第二个数据库。

该方案使行程、分类和花销可以在同一事务中保持一致；查询统计无需重写整趟行程；删除行程可依靠外键级联；数据库备份、锁和损坏检测继续覆盖全部本地数据。

## 4. 数据模型与迁移

### 4.1 数据库版本

数据库当前版本由 v2 升级到 v3。新数据库直接创建完整 v3 结构；已有 v2 数据库在任何结构修改前生成并校验备份，再在单一事务中迁移。为了保持旧用户兼容，启动入口继续支持从 v1 按顺序迁移到当前版本，但一次启动只需在首次修改前保留一份已验证的原始快照。

迁移完成后必须执行结构验证、`quick_check` 和外键检查。备份、迁移或验证失败时回滚并拒绝启动，不覆盖旧数据；失败产物不得被标记为有效备份。

### 4.2 `expenses`

每笔花销保存：

```text
id: string, primary key
trip_id: string, foreign key -> trips(id), on delete cascade
revision: positive integer
amount_cents: positive safe integer
category_id: stable default/custom category id
city_code: six-digit city code or null
city_name: city-name snapshot or null
spent_date: YYYY-MM-DD
note: string, at most 200 characters
created_at: ISO timestamp
updated_at: ISO timestamp
```

新建花销只能选择当前路线城市或“整个行程”。编辑历史花销时，可以保留已移出路线的城市，也可以改为当前路线城市或“整个行程”。

### 4.3 `expense_categories`

每个自定义分类保存：

```text
id: string, primary key
trip_id: string, foreign key -> trips(id), on delete cascade
revision: positive integer
name: trimmed display name
normalized_name: normalized name, unique within trip
created_at: ISO timestamp
updated_at: ISO timestamp
```

七个默认分类使用代码常量，不写入该表。默认与自定义 ID 使用不同前缀。花销只保存分类 ID，因此重命名自定义分类会同步影响历史花销的显示名称。

### 4.4 操作回执

新增通用的花销模块操作回执表，保存操作 ID、实体类型、实体 ID、行程 ID、请求摘要和有界响应。新增、编辑或删除的响应丢失时，客户端可以重发完全相同的命令并得到相同结果，不重复创建记录。操作 ID 被复用于不同请求时返回冲突。

## 5. 模块边界

- `expense-categories`：默认分类、名称规范化和分类目录解析。
- `expense-validation`：金额、日期、分类、城市和备注校验，以及人民币元到分的精确转换。
- `expense-store`：花销 CRUD、版本检查、操作回执和数据库行验证。
- `expense-category-store`：当前行程自定义分类 CRUD、版本检查和使用状态保护。
- `expense-statistics`：总额、预算剩余、分类汇总、城市汇总和稳定排序，不修改输入。
- `expense-service`：组合行程、花销和分类存储，在事务内执行业务命令。
- `expense-api-router`：提供本机同源 JSON API，并沿用现有请求大小、内容类型和来源保护。
- `expense-controller`：页面加载、提交、冲突恢复、删除确认和路由生命周期。
- `expense-views`：只负责安全渲染，不重复业务规则。

既有 `travel-service` 在删除行程时继续处理草稿与 AI 转换标记；数据库外键在同一事务中级联删除花销和分类。任何一步失败都会整体回滚。

## 6. API 与数据流

接口挂在具体行程下：

- `GET /api/trips/:tripId/expenses`：返回行程花销总览、分类目录、统计和明细。
- `GET /api/trips/:tripId/expenses/:expenseId`：返回单笔可编辑记录。
- `PUT /api/trips/:tripId/expenses/:expenseId`：以客户端生成的 ID、操作 ID 和预期版本新增或编辑。
- `DELETE /api/trips/:tripId/expenses/:expenseId`：以操作 ID 和预期版本删除。
- `GET /api/trips/:tripId/expense-categories`：返回默认与自定义分类及使用状态。
- `PUT /api/trips/:tripId/expense-categories/:categoryId`：新增或重命名当前行程的自定义分类。
- `DELETE /api/trips/:tripId/expense-categories/:categoryId`：删除未使用的自定义分类。

所有写操作先验证行程存在、实体归属、预期版本和字段，再在数据库事务中写入。服务端不信任客户端传入的分类名称、城市名称、统计值或预算结果；这些数据由服务端目录和存储记录重新计算。

## 7. 页面与交互

### 7.1 行程详情

行程详情新增花销卡片，显示累计花销、预算剩余和最近三笔记录，并提供“记一笔”和“查看全部”。没有花销时显示“—”与“尚无记录”；未设置预算时显示“未设置预算”。

### 7.2 花销总览

新增路由 `#/trips/:tripId/expenses`，页面依次展示：

1. 总花销和预算剩余。
2. 按分类汇总。
3. 按城市汇总，未关联城市的记录归入“整个行程”。
4. 按消费日期倒序、更新时间倒序、ID 稳定排序的明细。
5. 始终易于找到的“记一笔”和“管理分类”入口。

点击明细进入编辑页。删除前二次确认，确认文案包含格式化金额或安全截断的备注摘要；取消不改变数据。

### 7.3 新增与编辑

新增路由 `#/trips/:tripId/expenses/new`，编辑路由 `#/trips/:tripId/expenses/:expenseId/edit`。两者共用金额、分类、城市、日期和备注表单。

错误文字显示在对应字段附近，并聚焦第一个错误。保存期间防止重复提交。保存失败或版本冲突时保留全部输入；不自动覆盖另一标签页的修改，也不自动重复写操作。用户可在明确提示下重试相同命令或重新载入最新记录。

### 7.4 分类管理

新增路由 `#/trips/:tripId/expense-categories`。默认分类只读；自定义分类支持新增、重命名和删除。删除正在使用的分类时不写数据库，并提示先修改对应花销。

### 7.5 首页集成

首页花销概览从占位状态升级为全部正式行程已记录花销的累计金额。完全没有记录时仍显示“尚无记录”，不把缺失数据显示成虚假的 `¥0`。本阶段不增加全局记账导航入口，所有花销操作从具体行程进入。

### 7.6 视觉与响应式

沿用现有暖色设计系统。总额、预算和分类统计使用紧凑卡片；桌面端充分利用横向空间，窄屏改为单列。超支使用暖红色，但必须同时显示负数与文字。表单标签、错误关联、键盘焦点和触控区域符合现有可访问性约束。

## 8. 校验与一致性规则

- 金额拒绝空值、零、负数、科学计数法、多于两位小数以及超出安全整数范围的结果。
- 日期拒绝非法格式和行程范围外日期。
- 分类必须是默认分类或属于当前行程且仍存在的自定义分类。
- 城市必须为空、属于当前路线，或在编辑时等于该记录已经保存的历史城市。
- 分类名称去除首尾空格后不能为空；按规范化名称检查重复。
- 自定义分类被任何花销使用时，删除命令失败且不产生写入。
- 所有编辑与删除使用实体版本；版本不匹配返回冲突并保留客户端输入。
- 页面切换或旧请求延迟返回时，旧响应不得覆盖当前路由。
- 日志只记录操作类型和错误代码，不记录金额、备注、分类名称、行程名称、城市选择或 API Key。

## 9. 错误处理

- 字段错误返回稳定字段代码和用户可理解的中文提示。
- 记录不存在、归属错误和版本冲突使用不同错误代码，页面分别处理。
- 请求结果不确定时保留同一操作 ID，允许安全重试；禁止用新操作 ID猜测性重复新增。
- 读取、统计或分类目录失败时展示错误状态与重试，不伪装成空列表或零金额。
- 删除失败时保留当前记录和页面状态。
- 数据库损坏、未知版本、迁移备份失败或迁移验证失败时拒绝启动，不自动重建数据库。

## 10. 测试与验收

自动化测试至少覆盖：

- 新建 v3 数据库，以及 v1/v2 到 v3 的备份、迁移、回滚与结构验证。
- 花销和分类 CRUD、行程归属、深拷贝/解析边界、版本冲突和操作回执幂等性。
- 金额精确转分、日期边界、备注长度、默认分类、自定义分类重名与使用中删除保护。
- 无预算、预算剩余、超支、分类汇总、城市汇总、明细稳定排序和历史城市显示。
- 行程删除时花销与分类级联清理，并验证事务失败不会部分提交。
- API 方法、路径、同源防护、错误映射和敏感数据不泄漏。
- 前端路由、表单状态、重复提交保护、延迟响应隔离、冲突保留、删除确认和页面刷新。
- 首页、行程详情和 AI 转正式行程后的花销入口。

浏览器验收使用独立 QA 数据库和模拟 AI 工厂，不连接真实或付费外部接口。至少验证多城市记录、整个行程归属、编辑、分类管理、超支、历史城市、删除取消/确认、刷新持久化、桌面与窄屏布局，以及 Console 无应用错误。

完整既有测试必须继续通过。README 同步改为从已合并的项目主目录启动，并移除“尚未合并”的过时说明。

## 11. 完成标准

- 用户能从任一正式行程完成花销新增、查看、编辑和删除。
- 默认分类与当前行程自定义分类符合全部规则。
- 总额、预算、分类和城市统计始终与明细一致。
- 无花销、无预算、超支、已移出路线和错误状态表达明确。
- 旧数据库安全升级，任何失败路径不破坏已有行程、AI 设置或攻略数据。
- 自动化测试、浏览器验收和文档更新完成。
- 不包含足迹地图、登录、云同步、分享和互联网部署；这些继续作为后续独立阶段。
