# 智游足迹网页版：产品路线与第一部分设计

日期：2026-10-02。状态：用户已确认正式设计；尚未开始产品代码实现。

## 1. 已确认的意图

用户保留现有微信小程序，按无 AI 方案继续开发；另做一个包含原计划全部核心功能及 AI 旅游规划的网站。网站和小程序相互独立，账号、存储和用户数据不互通，不改动已保留的 `codex/footprint-map` 分支。

网页版第一版仅供用户个人使用，在本机运行、通过浏览器打开。不购买域名、不租服务器、不公开发布、不启用注册或跨设备同步。沿用中国境内、多城市、人民币及个人旅行记录的业务范围。界面由开发者自由设计，后续用户会专门修改，不把当前视觉风格视为最终定稿。

成功标准：用户能在网页完成可靠的多城市行程管理；数据和草稿重启后仍存在；后续可分别加入 AI 规划、花销和足迹，而无需将小程序数据迁入。

## 2. 分期与产品边界

1. 网站基础与行程管理（本规格）：本机服务、独立数据库、首页、行程 CRUD、城市路线、草稿。
2. AI 旅游检索与规划：需求输入、带可核查来源的攻略、可编辑计划转行程；接入用户自己的模型凭据。具体检索服务、调用预算与输出规则在该阶段单独确认，不把模型自身知识声称为实时检索。
3. 行程花销：默认与行程内自定义分类、城市归属、金额/日期校验、预算及统计。
4. 中国足迹地图：自动点亮、历史补录、重复到访详情、删除行程保留足迹；地图授权及实际版图显示单独核验，不能直接把小程序测试地图素材公开发布。
5. 个人版收尾：数据备份/恢复、安全和体验检查、启动说明；若以后需要互联网部署或多用户，再另行设计认证、同步和费用控制。

每部分单独设计、实现和验收；完成当前部分后停下，由用户决定是否继续。第一部分不实现或调用 AI、不要求提供 API Key、不实现记账、地图、登录、分享或互联网部署。

## 3. 方案选择与技术架构

采用独立的本地网页应用：原生 HTML/CSS/JavaScript 前端、Node.js HTTP 服务、SQLite 数据库。无需前端框架、打包器或第三方服务器框架，控制首阶段依赖和维护成本。已在本机确认 Node.js v25.9.0 可使用 `node:sqlite` 的 `DatabaseSync` 执行 SQLite 查询；运行文档固定此已验证环境，不假设其他版本等价。

备选纯前端浏览器存储方案不作为本版主方案：它适合界面原型，但持久化与未来服务器端 AI 凭据配置需要额外迁移。当前服务仅监听 `127.0.0.1`，桌面浏览器可访问；响应式手机布局只意味着窄屏兼容，不意味着手机能连接本机服务。

项目目录：`C:\Users\X\Documents\ChatGPT\智游足迹网页版`，与小程序仓库分开。数据库位于本项目运行数据目录，不在静态资源目录，也不提交到 Git。没有服务器进程运行时网页无法访问；停止服务不删除数据库。

模块职责：

- `domain`：日期、状态、城市、预算、路线校验，纯函数且不依赖 DOM、HTTP 或 SQLite。
- `storage`：数据库版本、事务、行程/草稿仓库；对损坏或不支持版本拒绝覆盖。
- `server`：静态文件白名单、请求体限制、请求校验、API 错误映射、仅本机监听。
- `web`：导航、展示、编辑表单、草稿恢复、请求状态；页面不直接操作数据库。

可参考现有小程序的纯业务规则、城市目录及测试用例，复制后由网站独立维护；不得读取小程序存储、依赖小程序运行时或建立跨项目写入链接。后续 AI 凭据只供服务端使用，不嵌入前端、日志或仓库。

## 4. 第一部分界面与流程

界面先采用暖米白、陶土橙、清晰卡片和克制的旅行氛围；桌面用侧边导航，窄屏用紧凑导航。优先可读性、键盘操作和清晰状态，不制作需要外部服务的图片或地图装饰。UI 后续可更换，不与业务规则耦合。

可用页面：

- 首页：最近行程、行程总数、待出发/进行中/已结束数量、新建入口。未实现的花销/足迹不显示假数字。
- 行程列表：状态分组、日期与城市摘要、空状态、查看/新建入口。
- 三步行程编辑：基本信息 → 城市路线 → 确认。新建和编辑复用流程。
- 行程详情：基本信息、城市时间线、编辑和二次确认删除。

不放置可点击但不可用的 AI、记账或地图入口。首页可用非交互文字说明后续开发范围。

基本信息：名称必填且去除首尾空格；开始/结束日期必填；出行人数为正整数；预算可空，只接受正的人民币金额、最多两位小数且转换为分后为安全整数。

路线：从现有 344 项中国城市目录搜索；至少一个城市；同一行程不得重复城市；上下移动调整顺序（本阶段不实现拖拽）；每城到达/离开日期必填，包含在行程范围内，允许同一天到达离开。只允许相邻且顺序正确的前城离开/后城到达共用一天，不允许其他重叠或逆序时间线。

确认页：展示全部输入，只有校验通过才允许保存。新建使用预先固定的行程 ID；重复点击/不确定的保存重试不会产生第二趟行程。保存和删除均显示进行中状态，防止重复提交。

草稿：输入变化后短暂防抖保存到独立草稿表；步骤切换时先保存草稿，失败不声称已保存。重新打开编辑入口时提示恢复或舍弃草稿；舍弃需要确认。草稿能容纳未填写或非法的表单字段，不当成正式行程。草稿携带目标行程 ID、当前步骤和编辑起点版本。正式保存及草稿清理放在同一数据库事务；保存失败保留草稿与屏幕输入。陈旧的异步草稿请求不能在正式保存后复活草稿。

删除：确认文案含行程名称；取消不改数据；确认后原子删除当前行程及其编辑草稿，成功后返回列表。此阶段不存在花销或足迹关联，后续阶段扩展生命周期服务，不在这里预先制造关联记录。

## 5. 数据与 API 契约

日期统一使用 `YYYY-MM-DD` 的真实日历日期；状态以本机服务当天日期计算，不持久化：开始日前待出发，起止日期内进行中，结束日之后已结束。时间戳为 ISO 格式。

`Trip`：`id`、`name`、`startDate`、`endDate`、`travelerCount`、可空 `budgetCents`、有序 `cities`、`createdAt`、`updatedAt`、单调递增 `revision`。

`TripCity`：`cityCode`、`cityName`、`provinceCode`、`provinceName`、`arrivalDate`、`departureDate`、`order`。新保存的编码必须属于网站独立城市目录；名称由服务端解析，不能信任客户端伪造。未来目录变化不自动擦除已有名称快照。

SQLite 包含元数据版本、行程、行程城市、草稿表；外键和事务确保写入完整。金额保存为整数分；草稿原始表单保留金额字符串，不经过浮点乘法存钱。第一次在空目录创建数据库；已有损坏文件、缺失元数据的非空数据库或未知版本不自动重建。单用户不等于单标签页：更新/删除必须匹配 `revision`，冲突报告 409 并要求重新加载，不静默覆盖另一标签页的修改。

API：

- `GET /api/overview`：最近行程、真实状态统计及服务端当天日期。
- `GET /api/trips` / `GET /api/trips/:id`：列表/详情；缺失记录返回 404。
- `PUT /api/trips/:id`：幂等的新建/版本受控更新；新建重试只在内容/身份一致时视为同一次保存；校验错误返回 422，冲突返回 409。
- `DELETE /api/trips/:id`：版本匹配才删除；重复删除不存在记录返回 404。
- `GET /api/cities?q=...`：标准目录搜索，最多返回 20 项。
- `GET/PUT/DELETE /api/drafts/:key`：新建草稿和按行程 ID 隔离的编辑草稿；写入具有草稿版本约束。正式保存请求带草稿版本，在同一事务保存行程并清除对应草稿。

错误体只包含错误代码、可展示消息及必要字段错误；日志不输出行程正文、预算、备注、数据库内容或凭据。静态服务只暴露前端资源，禁止路径穿越及读取数据库/配置。JSON 请求体限制为 64 KiB。拒绝非预期 Host；写 API 检查同源 Origin 和 JSON 内容类型，防止其他网页向本机服务写入。首阶段仅本机、无远程认证；若开放监听地址，必须先重新设计访问控制。

## 6. 错误、测试与验收

字段错误邻近字段，保留用户输入、聚焦首个错误。网络/数据库错误展示可理解的重试提示，不把加载失败显示成空行程。详情记录不存在时提供返回列表入口；版本冲突保留本地输入并提示先重新载入，未经确认不自动覆盖。

自动化测试：日期边界、人民币精确转分、城市搜索/重复/顺序/所有重叠情况；SQLite CRUD/重启持久化/事务回滚/版本和损坏保护；草稿恢复、提交身份与清理、陈旧写入拒绝；HTTP 状态、请求大小限制、同源写保护、路径穿越拒绝；页面事件与领域层接线。

浏览器验收：空状态 → 新建南京/苏州多城市行程 → 三步确认 → 首页/列表/详情一致 → 修改及重新排序 → 草稿关闭后恢复 → 取消删除/确认删除 → 重启服务保留数据。检查桌面及约 390px 窄屏，键盘焦点、表单错误、无控制台业务异常；数据文件不得经静态 URL 下载。

完成证据必须包括全套测试结果、真实浏览器交互与截图记录、未通过项，以及用户实际效果确认。自动化测试不能替代视觉验收。完成这一部分后暂停，不自动实施第二部分 AI。
